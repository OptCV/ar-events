# AGENTS.md — Authoritative AI Coding Rules

This file governs automated and AI-assisted changes. It takes precedence over generic agent preferences, but not over user instructions or repository security policies.

## Mandatory reading sequence (every session)

1. `README.md` and `MASTER_PROMPT.md` if new to the repository.
2. `PROGRESS.md` and `TASKS.md` for actual status.
3. `DECISIONS.md` for accepted architectural decisions.
4. `PLATFORM_ROUTING.md` and `CAPABILITIES.md` before touching any AR pipeline.
5. The owning detailed spec: `IMAGE_TO_AR.md`, `DATA_MODEL.md`, `ARCHITECTURE.md`, `DESIGN.md`, `TESTING.md`, or `SECURITY.md`.

## Hard constraints

- Use **Vite + React + TypeScript**, CSS Modules/plain CSS. **Never introduce Tailwind, shadcn, Next.js, or a UI framework** without explicit approval.
- Use **Hono on Cloudflare Workers**, **PostgreSQL + Drizzle + Hyperdrive**, **Cloudflare R2**, and durable async publishing through Workflows/Queues.
- Isolate Python/OpenUSD conversion in a containerized, constrained processing service.
- **Android image tracking: native experimental WebXR image/marker API only**. The browser flag may be required; never invent native support.
- **Android floor and wall: Google Scene Viewer**, not WebXR; wall uses `enable_vertical_placement=true` where supported.
- **iOS: AR Quick Look USDZ** for image/floor/wall with documented anchoring metadata.
- **Image-to-AR** creates GLB and USDZ preserving original image alpha; target tracking image is a distinct role.
- Scene Viewer must receive one **hosted, composed GLB**, not a browser `blob:` URL or transient JS-only scene.
- Treat Quick Look and Scene Viewer as limited native interfaces; unsupported interactive nodes must have visible fallbacks, not be silently dropped.

## Agent work protocol

### Before edits

- Restate the task in one sentence; identify affected modules and constraints.
- Inspect existing files, code, tests and migrations; do not infer project structure from a desired architecture.
- Search relevant docs; check compatibility claims against official platform documentation.
- Confirm whether a requirement is proven, assumed, experimental, or device-dependent.
- Plan the smallest vertical slice with runnable validation.

### During edits

- Keep one canonical typed scene schema; use `zod`/TypeScript for boundaries and version migrations.
- Maintain per-platform compile/launch adapters and centralized feature registry.
- Preserve uploads/originals; write derived assets under immutable versioned keys.
- Honor data ownership, safety limits and URL sanitization. Never execute untrusted uploaded scripts.
- Add tests alongside implementation. Prefer deterministic fixtures for conversions.
- Keep external app-launch links generated by a single audited utility.
- Never handcraft or rename a ZIP to USDZ. Use a proper USDZ packager.

### After edits

- Run applicable formatting, type checking, unit tests, build, schema and converter validation. Record actual commands and results.
- Update `TASKS.md` checkboxes, `PROGRESS.md` status and `CHANGELOG.md` summary.
- Update `CAPABILITIES.md` for feature behavior changes; `PLATFORM_ROUTING.md` for launch changes; add an ADR for material architectural changes.
- If real-device tests were not executed, label them **NOT TESTED**, with device/OS/browser requirements.
- Report implementation gaps, unsupported behavior and risks explicitly.

## Definition of done

A feature is not done if UI merely renders. It requires functional paths, boundary validation, relevant tests, honest failure states, and end-to-end output that matches the selected runtime.

A publishing pipeline is not done until asynchronous job orchestration, immutable storage, validation outcomes, fail-safe revision promotion and recovery paths are tested.

A native AR behavior is not **verified** until it has been tested on target hardware with recorded device/OS/browser versions.

## Naming and file conventions

Suggested modules: `apps/web`, `apps/api`, `packages/schema`, `packages/scene`, `packages/capabilities`, `packages/ui`, `services/usd-processor`, `tests/fixtures`. This is a target structure, not an assertion that these paths already exist.

Use `feature/` branch names, Conventional Commits if this project adopts Git, and ADR numbers in `DECISIONS.md`. Keep secrets only in environment/bindings, never committed examples.

## If blocked

Do not fabricate support, working server responses or device screenshots. Implement the part that can be proven; document a concrete blocker, alternatives, and test instructions. Never silently switch platform strategy.
